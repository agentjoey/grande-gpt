## 0. 为什么这个切片不适合自举

S1 / S1.5 / S2 都由 ChatGPT 经 GrandeGPT 实现。**S2.5 不行**，理由是结构性的：

**前端设计的核心反馈回路是「看」，而 ChatGPT 看不到渲染结果。**
它可以写出语法正确、测试通过的 React 组件，但无法判断间距是否失衡、层级是否清晰、
移动端是否可用。工作流 §6② 把这一点写成硬要求：「布局、层级、内容密度、交互或
响应式存在实质歧义时，**纯文字批准不充分**」。

所以本切片由我（Claude Code，有浏览器工具）实现，ChatGPT 不参与。

## 1. 这个控制台是给谁用的、解决什么

**唯一用户是你（Human Owner），在自己的机器上。**

它不是给团队看的看板，也不是给模型用的界面——模型有 MCP 工具。它要解决的是**我在
这几轮里反复手工干的那些事**：

| 我实际手敲过的 | 频次 |
|---|---|
| `node -e '...DatabaseSync...'` 查 task / job / audit 表 | 十几次 |
| `git worktree list` + `git branch --list 'grande/*'` 对账 | 每轮收尾 |
| `grep '\[tool\]' /tmp/grande-gateway.log` 看模型调了什么 | 排查时每次 |
| 自签 token 查 `tools/list`（客户端视角自检） | 那次故障排查 |
| `du -sh .grande-work/worktrees` 看磁盘 | 几次 |

**这是真实需求的证据，不是猜的。** 控制台的第一价值是把这些变成一屏。

### 1.1 明确不做的

- **不做「让模型干活」的入口**——那是 ChatGPT 的职责，控制台重复它只会制造两个真相源
- **不做多用户 / 分享 / 通知**（D2 单用户）
- **不做实时协作**——单人单机，轮询足够

## 2. 信息架构（三个页面）

```
/                 概览      现在怎么样了
/tasks/:taskId    任务详情  这个任务发生过什么
/audit            审计      谁在什么时候动了什么
```

**只有三个页面，这是有意的。** 工作流 §7 的设计红线里有「散乱微特效 = AI 味」，
同理散乱的页面 = 没想清楚。宁可三个页面各自完整，不要八个页面各自半吊子。

### 2.1 `/` 概览

一屏回答「现在怎么样」：

- **活跃任务卡片**：taskId、仓库、分支、改动文件数、最近 job 状态、base 落后几个 commit
- **Gateway 健康**：进程在不在、端口、issuer、schema 版本、最近一次工具调用时间
- **磁盘**：worktrees 占用、trash 占用、checkpoints 占用
- **对账告警**：孤儿 worktree 数、幽灵 task 数（`grande gc` 的 dry-run 结果）

### 2.2 `/tasks/:taskId` 任务详情

- 分支、base commit、base 分歧（`behind` / `diverged`）
- 改动文件列表 + diff
- job 时间线（profile、状态、耗时、退出码），点开看 artifact 尾部
- **attestation**（S2）：这个任务的哪些 commit 有本机验证记录
- 审计条目（只读，按时间倒序）

### 2.3 `/audit` 审计

按时间倒序的账本视图，可按 taskId / 工具名 / decision 过滤。
**这是被审计者不可写的记录**（D3），控制台也只读。

## 3. 破坏性操作：T3 的核心风险面

规格 §10.2 点名的三个破坏性操作：**worktree 清理、task 关闭、Policy 修改**。

### 3.1 我的建议：**第一版一个都不做**

**控制台先做纯只读。** 理由：

1. 这三个操作**都已经有可用入口**——`grande gc --apply`、`grande_task_close`、
   直接编辑控制平面 YAML。控制台重复它们不增加能力，只增加一个新的出错面
2. 破坏性操作的 UI 是最难做对的部分（确认语义、误触防护、操作后状态刷新、
   失败回滚提示），**而它们的价值最低**
3. **只读版能立刻用，而且不可能弄坏任何东西**

如果用一段时间后发现「每次都要切到终端去关任务」确实烦，再加——那时候有真实的
使用频次数据，也更清楚确认框该长什么样。

**这需要你确认。** 如果你希望第一版就带这些操作，本文件的 Tier 论证不变（仍是 T3），
但状态矩阵和 mockup 范围要相应扩大，人日往上调。

### 3.2 认证

即便只读，控制台也需要鉴权——它展示审计账本和仓库路径。

**建议：绑定到 `127.0.0.1`，不走隧道，不做登录页。**
理由：单用户、单机、且 Cloudflare Access 那套已经用在 `/mcp` 上了。
控制台不该成为第二个需要独立维护的认证面。

**明确的取舍**：这意味着控制台**只能在本机访问**。你在手机上看不到它。
如果你要远程访问，那就需要走隧道 + Access，人日往上调，且 T3 的认证触发器
从「本地绑定」变成真正的认证实现。**这也需要你确认。**

## 4. 状态矩阵（T3 必须，工作流 §6①）

每个页面的所有适用状态。**这一节是 mockup 必须覆盖的清单。**

| 页面 | loading | empty | error | success | permission |
|---|---|---|---|---|---|
| `/` | 骨架屏（首屏 < 1s） | **无活跃任务**——不是错误，是常态，要有明确的「一切正常」表达 | Gateway 未运行 / 状态库 schema 不匹配（两者文案不同） | 正常渲染 | 非本机访问 → 拒绝 |
| `/tasks/:id` | 骨架屏 | 任务无改动 / 无 job | taskId 不存在（404 而非空白） | 正常渲染 | 同上 |
| `/audit` | 骨架屏 | 过滤后无结果（≠ 账本为空，两者文案不同） | 状态库读失败 | 正常渲染 | 同上 |

**两个容易被做成「空白页」的状态，我特意拆开了**：
- `/` 的 empty（没有活跃任务）是**最常见的状态**，不是边缘情况
- `/audit` 的「过滤后无结果」和「账本本身是空的」必须给出不同文案，
  否则用户不知道是自己筛错了还是真没有

### 4.1 响应式

- **桌面优先**——这是运维工具，主要在桌面用
- 但**必须在移动端可读**：那次 ChatGPT 权限故障我是在你发手机截图时排查的，
  你在手机上看一眼「任务现在什么状态」是真实场景
- **不把桌面布局压缩成移动布局**（工作流 §6① 明确禁止）：移动端只保留概览的
  任务卡片与告警，表格类内容改为卡片流

## 5. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | Next.js（App Router） | 工作流 §适用范围就是 React/Next.js；且 urbanbricks 已在用，你熟 |
| 样式 | Tailwind | 同上 |
| 组件 | shadcn（走 MCP/CLI，见工作流 §6③） | 强制要求 |
| 数据来源 | **直接读 `~/.grande-control/state/grande.db`（只读连接）** | 不经 Gateway——控制台挂了不该影响 MCP 服务，反之亦然 |
| 动效 | 第一版**几乎不做** | 工作流 §6④：动效集中在高影响时刻。运维工具没有高影响时刻 |

### 5.1 一个必须早定的技术决定

**控制台是独立进程还是挂在 Gateway 里？**

**建议独立**。Gateway 的职责是服务 ChatGPT，把一个 Next.js 应用挂进去会：
- 让 Gateway 的重启影响控制台（反之亦然）
- 把前端依赖拖进一个目前只有 6 个运行时依赖的进程
- 让沙箱与端口配置变复杂

代价是多一个要启动的东西。**可接受**——它本来就是按需打开的。

## 6. 设计方向与至少一项有意图的选择（工作流 §6① 要求）

**方向：仪表盘不是控制台，是「体检报告」。**

参考的不是 Vercel/Linear 那类操作型控制台，而是**监控面板**——你打开它是为了知道
「有没有事」，不是为了做事。所以：

- **告警优先于数据**：孤儿 worktree、schema 不匹配、Gateway 未运行这类要顶在最上面，
  而不是埋在某个 tab 里
- **默认视图不需要交互就有信息量**：不做「请选择一个任务」这种空手起步的页面

**一项有意图的设计选择：`/` 的空状态要设计成正面反馈，而不是留白。**

没有活跃任务是这个系统的**常态**（你大部分时间不在跑任务）。多数仪表盘在这时给你
一个灰色的「暂无数据」，那是把最常见的状态做成了最没信息的一屏。

我要做的是：空状态展示**上一个任务的结束摘要 + 当前系统健康 + 磁盘占用**，
让「没事」这个状态本身携带信息。
