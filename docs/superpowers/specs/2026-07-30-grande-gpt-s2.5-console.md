## 1. 这个控制台是给谁用的、解决什么

**唯一用户是你（Human Owner），在自己的机器上。**

它不是给团队看的看板，也不是给模型用的界面——模型有 MCP 工具。它要解决的是**我在
这几轮里反复手工干的那些事**：

| 我实际手敲过的 | 频次 |
|---|---|
| `node -e '...DatabaseSync...'` 查 task / job / audit 表 | 十几次 |
| `git worktree list` + `git branch --list 'grande/*'` 对账 | 每轮收尾 |
| `grep '\[tool\]' /tmp/grande-gateway.log` 看模型调了什么 | 排查时每次 |
| 自签 token 查 `tools/list`（客户端视角自检） | 那次故障排查 |
| `du -sh .grande-work/worktrees` 看磁盘 | 几次 |

**这是真实需求的证据，不是猜的。** 控制台的第一价值是把这些变成一屏。

### 1.1 明确不做的

- **不做「让模型干活」的入口**——那是 ChatGPT 的职责，控制台重复它只会制造两个真相源
- **不做多用户 / 分享 / 通知**（D2 单用户）
- **不做实时协作**——单人单机，轮询足够

## 2. 这是一个 dashboard，不是一个控制面板

**Human Owner 2026-07-31 的批评：「控制台不只是功能控制，也是 dashboard。重新设计。」
批评成立。** 上一版整节都在讨论「暴露哪些破坏性操作」，页面只有名字没有内容——
写着「体检报告」的方向，做的却是操作清单。

重新设计的起点不是 dashboard 模板，是**这个系统的真实账本里到底有什么**。
下面每个数字都来自 2026-07-31 查库，不是设想。

### 2.1 先看真实数据长什么样

```
audit 236 行                          job 103 个
  repo_edit  ALLOWED SUCCEEDED  108     unit-selfhost  failed 31  ← 各占一半
  run        ALLOWED SUCCEEDED  103     unit-selfhost  passed 31  ←
  repo_edit  ALLOWED FAILED      10     typecheck      passed 25
  task_open  ALLOWED SUCCEEDED    6     unit           failed  3
  push       ALLOWED FAILED       2     probe-slow     killed  1   ← 超时兜底真的触发过
  repo_edit  ALLOWED INTENT       1  ⚠  probe-slow     passed  1
  run        PENDING FAILED       1  ⚠
```

**三个发现直接改写了设计：**

#### ① 失败的 job 不是异常，是 TDD 的正常一半

`unit-selfhost` **31 失败 / 31 通过，正好各半**。这不是故障率，这是
「先写失败的测试，再让它通过」在账本里的样子。

一个朴素 dashboard 会把它渲染成「50% 失败率」的红色告警——**那是纯噪音，
而且会训练你忽略告警**。这是本设计最重要的一条约束：

> **计数不等于洞察。任何指标在渲染成告警之前，必须先回答「它异常的判据是什么」。**

对 job 失败率，正确的判据不是绝对值，而是**同一个 task 里连续失败且没有后续通过**
——那才是「卡住了」。孤立的失败是健康的开发节奏。

#### ② 账本里有两行真实异常，而现在没有任何东西会告诉你

| opId | 症状 |
|---|---|
| `op_5e3ed471…` | `grande_repo_edit` 卡在 `INTENT`，**从未推进到终态**（2026-07-30 18:07） |
| `op_f815ee64…` | `grande_run` 的 `decision=PENDING` 但 `state=FAILED`，reason 是「审计句柄推进失败——Policy 未放行或已被他人使用」 |

审计账本的状态机是 `PENDING→ALLOWED→EXECUTING→终态`。**卡在中间态的行就是异常**，
判据清晰、不需要阈值、不会误报。这类才配当告警。

**它们已经在库里躺了一天多，而我是为了写这份设计去查才发现的。** 这就是这个
dashboard 存在的理由——不是「让 CLI 变好看」。

#### ③ 一个已发布的功能从未产出过任何东西

`attestation` 表 **0 行**。S2 的 Verification Attestation 做完并合并了，
而 3 次 commit 一次都没签发——`grande_commit` 每次都说「当前工作区状态没有
对应的通过验证记录」。

**这不是 dashboard 能修的 bug，但正是 dashboard 该让你看见的事实。**
一个「功能签发率 0/3」的数字，比任何文档都更早告诉你某个环节没接上。

### 2.2 四个问题，四个页面

Dashboard 的结构不该来自数据表，该来自**你打开它时想知道什么**。

| 页面 | 它回答的问题 | 主体内容 |
|---|---|---|
| `/` **概览** | **「现在有事吗？」** | 判据明确的异常（卡态审计行、幽灵 task、schema 不符、Gateway 未运行）；卷可用空间；活跃任务卡片；**没有事的时候展示上一次任务的结束摘要**（§6） |
| `/tasks/:id` **任务** | **「这个任务进行得怎么样？」** | 改动文件与行数、job 时间线（RED→GREEN 的节奏应当看得出来）、checkpoint 链、有没有 commit / attestation / push / PR |
| `/audit` **账本** | **「刚才到底发生了什么？」** | 236 行的可筛选流水。**这是唯一能重建「模型做了什么」的地方**，也是异常的来源 |
| `/connections` **连接** | **「谁能连进来？还能断开吗？」** | OAuth client（3）、refresh 链（7，含 valid 状态）、当前 token epoch、**「彻底断开」** |

**为什么是这四个而不是别的**：它们对应四类时间尺度——此刻（概览）、
一个任务的一生（任务）、全部历史（账本）、持续存在的授权关系（连接）。
数据表反而是次要的：`job` 同时出现在概览与任务页，`audit` 同时是账本页的主体
与概览页告警的来源。

### 2.3 明确不做的

- **不做「所有表的 CRUD 界面」**——那是数据库客户端，不是 dashboard
- **不做实时推送**——按需打开的运维工具，手动刷新 + 可选轮询足够
- **不做趋势图表**：样本量太小（103 个 job、6 个 task），画出来的曲线是噪音的
  可视化。有意义的趋势需要几个月的数据，那时再说
- **不做「模型行为分析」**——审计账本能支撑，但那是产品功能不是运维工具

## 3. 破坏性操作：完整清单

**Human Owner 问「具体有哪些」——从代码里清点，不凭印象。**

### 3.1 系统里已存在的（控制台可能暴露）

| # | 操作 | 现有入口 | 不可逆程度 |
|---|---|---|---|
| D1 | **关闭任务** —— 删 worktree + 删分支 + 置 `CLOSED` | `grande_task_close`（MCP，ChatGPT 会弹确认框） | **高**：未提交改动永久丢失。全系统唯一 `destructiveHint: true` 的工具 |
| D2 | **回收孤儿 worktree** —— `git worktree remove` + `git branch -D` | `grande gc --apply` | **高**：同上，且孤儿按定义没有 task 行可查 |
| D3 | **改 Policy / 配置** —— `repos` / `profiles` / `deny` / `access` / `identity` 五个 YAML | 直接编辑文件 | **中**：可改回，但**改错 `access.yaml` 会锁死自己**；`deny.yaml` 现已承载 `readOnlyPaths`（2026-07-30 配置），改错等于放宽沙箱外执行面 |
| D4 | **吊销 access token** | ✅ **`grande revoke --yes` 已实现（2026-07-30）** | **中**：吊销后需在 ChatGPT 里重新授权 |
| D4b | **吊销 refresh token** | 仍无入口——只能手工 `UPDATE oauth_refresh SET valid=0`（遗留 #14） | **中**：`revoke` 不含这一步，控制台若做「彻底断开」必须两步都做 |

### 3.2 控制台可以新增的（目前完全没有入口）

| # | 操作 | 为什么现在没有 |
|---|---|---|
| D5 | **杀掉在跑的 job** | 只能手工 `kill -TERM -<pgid>`。没有工具，也没有 CLI |
| D6 | **回滚到某个 checkpoint** | `grande_rollback` 只在 MCP 层，CLI 没有 |
| D7 | **清理 trash / checkpoints** | 属 S4 保留策略，尚未做。当前 checkpoints 已 344K 且只增不减 |

### 3.3 操作挂在它所属的观察对象上，不做独立的「操作面板」

上一版把操作分三档列成一张表——那还是「控制面板」的思路。dashboard 的做法是：
**你正看着某样东西，然后想对它做点什么。** 操作没有自己的页面。

| 页面 | 你在看什么 | 顺手要做的 | 档 |
|---|---|---|---|
| `/` 概览 | 一个卡在 `INTENT` 的审计行 | **标记为已知**（不是删除——账本不可篡改，只加一条「已人工确认」） | 新增 |
| `/` 概览 | 卷可用空间告急 | **回收**（D2 gc）——展示将删什么、按§3.5 口径估算真实腾出量 | 强确认 |
| `/tasks/:id` | 一个跑了 90 秒还没结束的 job | **杀掉它**（D5） | ✅ 净增 |
| `/tasks/:id` | checkpoint 链，发现上一步改错了 | **回滚到某个 checkpoint**（D6） | ✅ 净增 |
| `/connections` | refresh 链里有一条陌生的 | **彻底断开**（D4 + D4b 两步合一） | 强确认 |

**不做的仍然不做**：D1 关任务（ChatGPT 里已有带确认框的入口，更合适）、
D3 改配置（YAML 编辑器 UI 是另一个项目，且改错 `access.yaml` 会把你锁在门外）、
D7 清 trash（等 S4 定保留策略）。

**「标记为已知」是这一版新增的，而且它是唯一一个不带风险的「操作」**——
账本不可篡改是铁律，所以它只追加一条确认记录，不修改原行。
没有它的话，那两行异常会永远挂在首屏，两天后你就开始无视整个告警区。

### 3.4 认证（你已定：远程访问）

既然要经 Cloudflare Tunnel 绑域名，**控制台必须有真实认证**，不能只绑 `127.0.0.1`。

**建议复用 `/mcp` 那一套**：Cloudflare Access 挡在前面 + 服务端校验
`Cf-Access-Jwt-Assertion`（JWKS RS256，`issuer` + `audience` 双验），
配置缺失 fail closed——`src/accessGate.ts` 已经实现了这些，直接复用。

⚠️ **`audience` 必须是控制台自己的 aud，不能复用 `/mcp` 的那个。**
Access 的 team domain 是共享的；`aud` 是唯一防止「拿着 MCP 的令牌访问控制台」的检查。
这一条与 D18 里 `aud` 的作用完全同源，也要有测试钉住。

### 3.5 ⚠️ 磁盘占用不能用 `du` —— 会高估 40 倍（2026-07-31 实测）

「体检报告」方向下磁盘占用是首屏要素，但**朴素实现会主动误导用户**。

`depDirs` 用 APFS clonefile（`cp -Rc`）把 `node_modules` 克隆进每个 worktree，
共享物理块；而 `du` 给每一份都完整计一遍。实测：

| 口径 | 数字 |
|---|---|
| `du` 报告一份 `node_modules` | **597M** |
| 克隆它时卷可用空间的实际变化 | **15M** |
| 单个 worktree 的自有内容（排除 depDirs） | 16.4M / 19.7M |

**高估约 40 倍。** `du -c` 也不去重（两个 worktree 各 635M 直接相加成 1.2G）。

后果不是「数字不好看」，而是**用户会为了腾出根本不存在的 1.2G 去删有用的 worktree**。
这也说明 S0.5 那次 gc 报告的「722M → 635M」同样是 du 口径、同样虚高，
CLAUDE.md 里那句「2 个任务已占 722M」应当理解为名义值。

**设计结论**（进状态矩阵，mockup 必须体现）：

- 首屏的磁盘卡片显示**卷的真实可用空间**（`df`），那是唯一不会骗人的数字
- 每个 worktree 显示**自有内容大小**（排除 `depDirs`），并把 depDirs 单列为
  「共享依赖（不占额外空间）」——**不要把两者相加**
- 「回收能腾出多少」必须按自有内容估算，且文案说明这是估算
- **绝不显示裸 `du` 总计**。如果某处必须显示，标注为「名义大小（含共享块）」

## 4. 状态矩阵（T3 必须，工作流 §6①）

每个页面的所有适用状态。**这一节是 mockup 必须覆盖的清单。**

| 页面 | loading | empty | error | success | permission |
|---|---|---|---|---|---|
| `/` | 骨架屏（首屏 < 1s） | **无活跃任务**——不是错误，是常态，要有明确的「一切正常」表达 | Gateway 未运行 / 状态库 schema 不匹配（两者文案不同） | 正常渲染 | Access JWT 缺失或 `aud` 不匹配 → 403（**不是登录页**，Access 挡在更前面） |
| `/tasks/:id` | 骨架屏 | 任务无改动 / 无 job | taskId 不存在（404 而非空白） | 正常渲染 | 同上 |
| **破坏性操作**（§3.3 已定档） | 执行中（按钮禁用 + 进度） | — | 失败要说清**做到哪一步了**（部分完成是真实情况） | 完成后状态刷新，**展示实际发生了什么**（删了几个、释放多少） | 无权限时按钮不渲染，不是渲染后再拒 |
| `/audit` | 骨架屏 | 过滤后无结果（≠ 账本为空，两者文案不同） | 状态库读失败 | 正常渲染 | 同上 |
| `/connections` | 骨架屏 | 无已注册 client（首次使用前的真实状态） | 读 oauth 表失败 | 3 个 client / 7 条 refresh / epoch=1 | 同上 |
| **磁盘卡片**（§3.5） | 测量中（`du` 在 600M 目录上要几秒，**不能阻塞首屏**） | — | 测不到（权限/路径不存在）时显示「未知」而不是 0 | 卷可用空间 + 每 worktree 自有大小 | — |

**两个容易被做成「空白页」的状态，我特意拆开了**：
- `/` 的 empty（没有活跃任务）是**最常见的状态**，不是边缘情况
- `/audit` 的「过滤后无结果」和「账本本身是空的」必须给出不同文案，
  否则用户不知道是自己筛错了还是真没有

### 4.1 响应式

- **桌面优先**——这是运维工具，主要在桌面用
- 但**移动端是一等公民，不是降级**：既然经隧道绑域名，你在手机上打开是常态场景。
  那次 ChatGPT 权限故障就是你发手机截图时排查的
- **破坏性操作在移动端要更谨慎**：误触成本更高，二次确认不能是一个容易划到的按钮
- **不把桌面布局压缩成移动布局**（工作流 §6① 明确禁止）：移动端只保留概览的
  任务卡片与告警，表格类内容改为卡片流

## 5. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | Next.js（App Router） | 工作流 §适用范围就是 React/Next.js；且 urbanbricks 已在用，你熟 |
| 样式 | Tailwind | 同上 |
| 组件 | shadcn（走 MCP/CLI，见工作流 §6③） | 强制要求 |
| 数据来源 | **直接读 `~/.grande-control/state/grande.db`（只读连接）** | 不经 Gateway——控制台挂了不该影响 MCP 服务，反之亦然 |
| 认证 | 复用 `src/accessGate.ts`（Cloudflare Access + JWKS RS256），**独立 `aud`** | 已实现且已实测。`aud` 是唯一防止拿 MCP 令牌访问控制台的检查 |
| 隧道 | 独立的 Cloudflare Tunnel + 独立域名 | 与 `grande.agentjoey.ai` 分开，便于单独吊销 |
| 动效 | 第一版**几乎不做** | 工作流 §6④：动效集中在高影响时刻。运维工具没有高影响时刻 |

### 5.1 一个必须早定的技术决定

**控制台是独立进程还是挂在 Gateway 里？**

**建议独立**。Gateway 的职责是服务 ChatGPT，把一个 Next.js 应用挂进去会：
- 让 Gateway 的重启影响控制台（反之亦然）
- 把前端依赖拖进一个目前只有 6 个运行时依赖的进程
- 让沙箱与端口配置变复杂

代价是多一个要启动的东西。**可接受**——它本来就是按需打开的。

## 6. 设计方向与有意图的设计选择（工作流 §6① 要求）

**方向：这是一份体检报告，不是一个驾驶舱。**

参考的不是 Vercel / Linear 那类操作型控制台——那些是「你来这里做事」的界面。
这里是「你来这里确认没事」的界面。多数时候你看一眼就该关掉。

因此：

- **告警优先于数据。** 判据明确的异常顶在最上面，而不是埋在某个 tab 里
- **默认视图不需要交互就有信息量。** 不做「请先选择一个任务」这种空手起步的页面
- **克制指标。** 样本量小（103 job / 6 task），任何比率都可能是噪音；
  §2.1① 已经给出一个具体例子——31/31 的「50% 失败率」实际是 TDD 的正常节奏

### 6.1 有意图的设计选择之一：空状态是主状态

没有活跃任务是这个系统的**常态**（你大部分时间不在跑任务）。
多数仪表盘在这时给一个灰色的「暂无数据」——那是把最常见的状态做成了最没信息的一屏。

这里的空状态要展示：**上一个任务的结束摘要 + 系统健康 + 卷可用空间**。
让「没事」这个状态本身携带信息，而不是留白。

### 6.2 有意图的设计选择之二：告警必须自带判据

每一条告警旁边写清**为什么它是异常**，而不只是「有 N 个问题」。

```
⚠ 1 个审计操作卡在中间态
  op_5e3ed471  grande_repo_edit  停在 INTENT  ·  2026-07-30 18:07
  判据：审计状态机是 PENDING→ALLOWED→EXECUTING→终态，
        停在中间态说明工具执行中断且没有留下终态记录
  [查看]  [标记为已知]
```

这不是文案洁癖。§2.1① 那条「50% 失败率」的反例说明：**说不清判据的指标不该做成
告警**。把判据写在旁边，等于强迫设计阶段就回答「这真的异常吗」——
写不出来的，就不该在首屏。

### 6.3 视觉方向

- **密度偏高、克制留白**：运维工具，一屏看完优于滚动三次
- **单色 + 一个强调色**，强调色只用于告警。不用多色状态标签——
  `passed`/`failed`/`killed` 用字重与位置区分，颜色只留给「需要你动手」的东西
- **等宽字体用于所有标识符**（opId / jobId / sha / 分支名）——它们要被复制粘贴
- **签名元素只有一处**：首屏的健康状态区。其余一律朴素

红线自查（工作流 §7）：无米色底、无 gradient text、无 border-left 色条、
无玻璃拟态、无 hero-metric 大数字（§2.3 已明确不做趋势图表）、
无 01/02/03 编号眉标、无同尺寸卡片无限重复。
