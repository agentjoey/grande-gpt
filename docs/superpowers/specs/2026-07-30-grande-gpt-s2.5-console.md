## 0. 为什么这个切片不适合自举

S1 / S1.5 / S2 都由 ChatGPT 经 GrandeGPT 实现。**S2.5 不行**，理由是结构性的：

**前端设计的核心反馈回路是「看」，而 ChatGPT 看不到渲染结果。**
它可以写出语法正确、测试通过的 React 组件，但无法判断间距是否失衡、层级是否清晰、
移动端是否可用。工作流 §6② 把这一点写成硬要求：「布局、层级、内容密度、交互或
响应式存在实质歧义时，**纯文字批准不充分**」。

所以本切片由我（Claude Code，有浏览器工具）实现，ChatGPT 不参与。

## 1. 这个控制台是给谁用的、解决什么

**唯一用户是你（Human Owner），在自己的机器上。**

它不是给团队看的看板，也不是给模型用的界面——模型有 MCP 工具。它要解决的是**我在
这几轮里反复手工干的那些事**：

| 我实际手敲过的 | 频次 |
|---|---|
| `node -e '...DatabaseSync...'` 查 task / job / audit 表 | 十几次 |
| `git worktree list` + `git branch --list 'grande/*'` 对账 | 每轮收尾 |
| `grep '\[tool\]' /tmp/grande-gateway.log` 看模型调了什么 | 排查时每次 |
| 自签 token 查 `tools/list`（客户端视角自检） | 那次故障排查 |
| `du -sh .grande-work/worktrees` 看磁盘 | 几次 |

**这是真实需求的证据，不是猜的。** 控制台的第一价值是把这些变成一屏。

### 1.1 明确不做的

- **不做「让模型干活」的入口**——那是 ChatGPT 的职责，控制台重复它只会制造两个真相源
- **不做多用户 / 分享 / 通知**（D2 单用户）
- **不做实时协作**——单人单机，轮询足够

## 2. 信息架构（三个页面）

```
/                 概览      现在怎么样了
/tasks/:taskId    任务详情  这个任务发生过什么
/audit            审计      谁在什么时候动了什么
```

**只有三个页面，这是有意的。** 工作流 §7 的设计红线里有「散乱微特效 = AI 味」，
同理散乱的页面 = 没想清楚。宁可三个页面各自完整，不要八个页面各自半吊子。

### 2.1 `/` 概览

一屏回答「现在怎么样」：

- **活跃任务卡片**：taskId、仓库、分支、改动文件数、最近 job 状态、base 落后几个 commit
- **Gateway 健康**：进程在不在、端口、issuer、schema 版本、最近一次工具调用时间
- **磁盘**：worktrees 占用、trash 占用、checkpoints 占用
- **对账告警**：孤儿 worktree 数、幽灵 task 数（`grande gc` 的 dry-run 结果）

### 2.2 `/tasks/:taskId` 任务详情

- 分支、base commit、base 分歧（`behind` / `diverged`）
- 改动文件列表 + diff
- job 时间线（profile、状态、耗时、退出码），点开看 artifact 尾部
- **attestation**（S2）：这个任务的哪些 commit 有本机验证记录
- 审计条目（只读，按时间倒序）

### 2.3 `/audit` 审计

按时间倒序的账本视图，可按 taskId / 工具名 / decision 过滤。
**这是被审计者不可写的记录**（D3），控制台也只读。

## 3. 破坏性操作：完整清单

**Human Owner 问「具体有哪些」——从代码里清点，不凭印象。**

### 3.1 系统里已存在的（控制台可能暴露）

| # | 操作 | 现有入口 | 不可逆程度 |
|---|---|---|---|
| D1 | **关闭任务** —— 删 worktree + 删分支 + 置 `CLOSED` | `grande_task_close`（MCP，ChatGPT 会弹确认框） | **高**：未提交改动永久丢失。全系统唯一 `destructiveHint: true` 的工具 |
| D2 | **回收孤儿 worktree** —— `git worktree remove` + `git branch -D` | `grande gc --apply` | **高**：同上，且孤儿按定义没有 task 行可查 |
| D3 | **改 Policy / 配置** —— `repos` / `profiles` / `deny` / `access` / `identity` 五个 YAML | 直接编辑文件 | **中**：可改回，但**改错 `access.yaml` 会锁死自己**，改错 `deny.yaml` 会放宽安全边界 |
| D4 | **吊销 OAuth client / refresh token** | 无入口——我那次故障是手工 `UPDATE oauth_refresh SET valid=0` | **中**：吊销后需在 ChatGPT 里重新授权 |

### 3.2 控制台可以新增的（目前完全没有入口）

| # | 操作 | 为什么现在没有 |
|---|---|---|
| D5 | **杀掉在跑的 job** | 只能手工 `kill -TERM -<pgid>`。没有工具，也没有 CLI |
| D6 | **回滚到某个 checkpoint** | `grande_rollback` 只在 MCP 层，CLI 没有 |
| D7 | **清理 trash / checkpoints** | 属 S4 保留策略，尚未做。当前 checkpoints 已 344K 且只增不减 |

### 3.3 我的建议：分三档，而不是「做/不做」

上一版我建议「一个都不做」，那是在人日受限的前提下。**你说人日无限制，所以该按风险
分档而不是按成本一刀切。**

| 档 | 操作 | 理由 |
|---|---|---|
| **✅ 第一版做** | D5 杀 job、D6 回滚 | 这两个**目前完全没有入口**，控制台是净增能力。且都可恢复：杀 job 不动文件，回滚本身进 Trash |
| **⚠️ 第一版做但要强确认** | D2 gc 回收、D4 吊销 OAuth | 有入口但难用（我每次手写 node 脚本）。**必须二次确认 + 展示将要删什么** |
| **❌ 第一版不做** | D1 关任务、D3 改配置、D7 清 trash | D1 已有更合适的入口（ChatGPT 里带确认框）；D3 改错能锁死自己，YAML 编辑器 UI 是另一个项目；D7 等 S4 定了保留策略再说 |

**这一档划分需要你确认**，它直接决定 mockup 要覆盖的状态矩阵范围。

### 3.4 认证（你已定：远程访问）

既然要经 Cloudflare Tunnel 绑域名，**控制台必须有真实认证**，不能只绑 `127.0.0.1`。

**建议复用 `/mcp` 那一套**：Cloudflare Access 挡在前面 + 服务端校验
`Cf-Access-Jwt-Assertion`（JWKS RS256，`issuer` + `audience` 双验），
配置缺失 fail closed——`src/accessGate.ts` 已经实现了这些，直接复用。

⚠️ **`audience` 必须是控制台自己的 aud，不能复用 `/mcp` 的那个。**
Access 的 team domain 是共享的；`aud` 是唯一防止「拿着 MCP 的令牌访问控制台」的检查。
这一条与 D18 里 `aud` 的作用完全同源，也要有测试钉住。

## 4. 状态矩阵（T3 必须，工作流 §6①）

每个页面的所有适用状态。**这一节是 mockup 必须覆盖的清单。**

| 页面 | loading | empty | error | success | permission |
|---|---|---|---|---|---|
| `/` | 骨架屏（首屏 < 1s） | **无活跃任务**——不是错误，是常态，要有明确的「一切正常」表达 | Gateway 未运行 / 状态库 schema 不匹配（两者文案不同） | 正常渲染 | Access JWT 缺失或 `aud` 不匹配 → 403（**不是登录页**，Access 挡在更前面） |
| `/tasks/:id` | 骨架屏 | 任务无改动 / 无 job | taskId 不存在（404 而非空白） | 正常渲染 | 同上 |
| **破坏性操作**（§3.3 已定档） | 执行中（按钮禁用 + 进度） | — | 失败要说清**做到哪一步了**（部分完成是真实情况） | 完成后状态刷新，**展示实际发生了什么**（删了几个、释放多少） | 无权限时按钮不渲染，不是渲染后再拒 |
| `/audit` | 骨架屏 | 过滤后无结果（≠ 账本为空，两者文案不同） | 状态库读失败 | 正常渲染 | 同上 |

**两个容易被做成「空白页」的状态，我特意拆开了**：
- `/` 的 empty（没有活跃任务）是**最常见的状态**，不是边缘情况
- `/audit` 的「过滤后无结果」和「账本本身是空的」必须给出不同文案，
  否则用户不知道是自己筛错了还是真没有

### 4.1 响应式

- **桌面优先**——这是运维工具，主要在桌面用
- 但**移动端是一等公民，不是降级**：既然经隧道绑域名，你在手机上打开是常态场景。
  那次 ChatGPT 权限故障就是你发手机截图时排查的
- **破坏性操作在移动端要更谨慎**：误触成本更高，二次确认不能是一个容易划到的按钮
- **不把桌面布局压缩成移动布局**（工作流 §6① 明确禁止）：移动端只保留概览的
  任务卡片与告警，表格类内容改为卡片流

## 5. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | Next.js（App Router） | 工作流 §适用范围就是 React/Next.js；且 urbanbricks 已在用，你熟 |
| 样式 | Tailwind | 同上 |
| 组件 | shadcn（走 MCP/CLI，见工作流 §6③） | 强制要求 |
| 数据来源 | **直接读 `~/.grande-control/state/grande.db`（只读连接）** | 不经 Gateway——控制台挂了不该影响 MCP 服务，反之亦然 |
| 认证 | 复用 `src/accessGate.ts`（Cloudflare Access + JWKS RS256），**独立 `aud`** | 已实现且已实测。`aud` 是唯一防止拿 MCP 令牌访问控制台的检查 |
| 隧道 | 独立的 Cloudflare Tunnel + 独立域名 | 与 `grande.agentjoey.ai` 分开，便于单独吊销 |
| 动效 | 第一版**几乎不做** | 工作流 §6④：动效集中在高影响时刻。运维工具没有高影响时刻 |

### 5.1 一个必须早定的技术决定

**控制台是独立进程还是挂在 Gateway 里？**

**建议独立**。Gateway 的职责是服务 ChatGPT，把一个 Next.js 应用挂进去会：
- 让 Gateway 的重启影响控制台（反之亦然）
- 把前端依赖拖进一个目前只有 6 个运行时依赖的进程
- 让沙箱与端口配置变复杂

代价是多一个要启动的东西。**可接受**——它本来就是按需打开的。

## 6. 设计方向与至少一项有意图的选择（工作流 §6① 要求）

**方向：仪表盘不是控制台，是「体检报告」。**

参考的不是 Vercel/Linear 那类操作型控制台，而是**监控面板**——你打开它是为了知道
「有没有事」，不是为了做事。所以：

- **告警优先于数据**：孤儿 worktree、schema 不匹配、Gateway 未运行这类要顶在最上面，
  而不是埋在某个 tab 里
- **默认视图不需要交互就有信息量**：不做「请选择一个任务」这种空手起步的页面

**一项有意图的设计选择：`/` 的空状态要设计成正面反馈，而不是留白。**

没有活跃任务是这个系统的**常态**（你大部分时间不在跑任务）。多数仪表盘在这时给你
一个灰色的「暂无数据」，那是把最常见的状态做成了最没信息的一屏。

我要做的是：空状态展示**上一个任务的结束摘要 + 当前系统健康 + 磁盘占用**，
让「没事」这个状态本身携带信息。
